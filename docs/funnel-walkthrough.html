FighterBot · Pipeline Walkthrough

Raw headlines in. Verified claims out.

Every gate the hourly hunt runs an article through, in order, illustrated with real items pulled from the live archive — not invented examples. The three tracked subjects are shown as Subject A/B/C, matching the rest of the repo — except inside quoted headlines, where the pseudonym stays "Fighter" so the quote doesn't read like it was edited. Everyone else named below is real.

This page covers the funnel only — discovery through claims. For the whole system (the Telegram service, operations, cost, the autonomous improvement loop) see docs/architecture-overview.html in the repo; for how it's tested, see docs/test-suite-overview.html.

§1Discovery — two rails, one window

Every hour, for every tracked subject: Google News RSS, queried once per language edition the subject gets covered in (English always; Ukrainian and Spanish where it applies), plus six direct publisher feeds — UFC.com, MMA Fighting, Bloody Elbow, Sherdog, Sport.ua, Marca — fetched once per run and filtered per subject by matching surname stems in both scripts. Both rails only look at the last 24 hours.

One real run: 6 outlets fetched, 180 items pooled across all three subjects — of which 5 were unseen for Subject C. — docs/checkin-log.md, 2026-08-09

The 24-hour window overlapping the hourly cadence ~24× is deliberate: a single failed run loses nothing, because the next run re-covers the same ground.

§2Gate 1 — Have we already seen this URL?

Exact match on url or its decoded resolved_url against everything ever stored → dropped silently, no database write at all. This is the only gate that costs nothing — no embedding, no fetch, no LLM call.

The database has no record of this gate — dropped items are never written. Cloud Logging does: across every scheduled run since 2026-08-07, 1,208 URL checks → 85 new (93% already known, dropped). See Fig. 1.

Survivors are capped at 5 unseen items per subject per run, newest first, applied after this gate — so on a busy day the newest 5 unseen items go through now, and whatever's left over is simply picked up next run. Nothing is lost, only delayed.

§3Gate 2 — Same story, different link?

The survivor's headline is embedded and compared against the subject's recent items. Cosine similarity ≥ 0.80 → held back, never posted — but not discarded: it inherits whatever claim its nearest neighbour already supports, recorded as corroboration for free, no LLM spent. The threshold is measured, not guessed: a real translated pair of the same story scored 0.841; unrelated same-subject pairs never rose above 0.702.

37 of 90 items were held here — the single biggest gate in the funnel.

"Fighter C's manager claims he'd beat every Ali Abdelaziz fighter: 'If we fought Gaethje again…'"

Official sources (UFC.com) are exempt from this gate specifically — a confirmation headline is, by construction, near-identical to the rumor it confirms, so holding it here would swallow the exact transition the claims layer exists to catch. And inheritance itself is checked: if an item actually reads closer to some other claim than the one it's about to be linked to, it stays held but unlinked rather than becoming a wrong piece of evidence. Both mechanisms are detailed in docs/architecture-overview.html §4.

§4The body step — reading past the headline

Only for items that survived both free gates. Google's wrapped URL is decoded to the real article address, then the body is extracted through a ladder — cheapest and most reliable first — and every attempt is logged, success or failure:

§5Gate 3 — What is this article actually about?

One Haiku call per survivor: the headline, source, a body excerpt when there is one, and every currently active claim for the subject. Forced tool use means the answer is always one of five verdicts — never free text to parse.

§6Digest tier — does this earn its own headline?

Every NO_CLAIM or UNSURE item — the ones with no claim to anchor a decision to — gets one more check before posting: does its own headline name the subject? If not, and the body is long enough to judge (≥300 characters) and names the subject at most once, it folds into a single shared "↘ Also mentioning" line instead of taking a bullet of its own.

The Subject C / Salkilld story, end to end The Sports Illustrated item from §4 is a NO_CLAIM: about Salkilld, not Subject C, who appears in exactly one sentence. It should have folded into "also mentioning." Because that sentence was doubled by the extraction bug, the mention count read 2 instead of 1 — one over the threshold — and it kept a full headline in the Subject C digest it hadn't earned. The tier rule was never wrong; the body handed to it was.

This tier is new enough (2026-08-09) that it has fired only 6 times in the live archive so far: 5 "main" (including this one, pre-fix) and, as of this snapshot, one genuine "tangential" — a Mark Zuckerberg viral-video story that named Subject C once in passing. That run had nothing else to post for Subject C, so the item wasn't folded into an "Also mentioning" line — it was suppressed outright instead: a message with nothing but a header and one shared line is exactly the noise this rule exists to remove, so nothing was sent for Subject C that run at all.

§7Claims — the distilled output

Everything the funnel does exists to feed this table. A claim is one row per real-world fact: a canonical English sentence, a type, a status that starts as rumor and moves to confirmed only when an official source asserts it. Everything MATCH-linked above is corroboration recorded against exactly one such row.
